Commands · Keep the library healthy

Maintain

Look up any command's spec, re-check papers for retractions, rebuild the search index from the files on disk, see what's configured, and move papers into Papers.app and your annotations back out. Files are the authority; these commands refresh projections and flag what changed without rewriting history.

How they fit

Commands

/ref:maintain

phase 11+mostly read-only

Run a compact maintenance cycle: status, lint, optional index rebuild, and optional retraction audit.

/ref:maintain [--stale-days <N>] [--no-index] [--no-audit] [--verbosity quick|normal|verbose]

Arguments

--stale-days <N>
Lint stale threshold in days. Default 180.
--no-index
Skip catalog rebuild.
--no-audit
Skip retraction-status sweep.
--verbosity
Passed to /ref:status. Default quick.

What happens

  1. Runs /ref:status first, to print a fast health snapshot.
  2. Runs /ref:lint with --snapshot to bucket PMIDs by maintenance issue class and record a timestamped report under maintenance/.
  3. Unless skipped, runs /ref:index --rebuild (and relation refresh when graph relations exist).
  4. Unless skipped, runs /ref:audit in default retraction mode.
  5. Prints compact next actions based on what those stages found.

Reads & writes

Reads everything status/lint/audit read. Writes a lint snapshot under maintenance/, plus whatever index/audit write when those stages are enabled.

Example

illustrative output

› /ref:maintain --stale-days 180
status:
status: needs full text

lint:
- abstract_only: 18 [...]

index:
catalog rebuilt: ...

audit:
changed_pmids: []

next:
- /ref:fetch <pmid...>
- /ref:extract <pmid...>

/ref:help

phase 0read-only

Quick-start tour: list every /ref:* command grouped by what it's for, or show one command's full spec without leaving the terminal. No library required.

/ref:help /ref:help <command>

Arguments

<command>
Optional. The bare command name with or without its ref-//ref: prefix — status, ref-status, and /ref:status all resolve the same way.

What happens

  1. With no argument: checks whether a library is configured. If not, leads with a pointer to /ref:init <path>. Then prints the grouped overview verbatim — every line a real command and description, not a summary written fresh each time. If a library is configured, closes with a pointer to /ref:status.
  2. With a command name: resolves it to its command file (stripping a leading /ref: or ref-), then prints that file's own spec unparaphrased. If no such command exists, says so and suggests the closest matches, or points at the grouped overview.

Reads & writes

Reads ~/.config/ref-manager/config.json to decide which closing pointer to print, and the target command's own file when one is named. Writes nothing.

Example

looking up one command

› /ref:help status
Quick-start tour: list every `/ref:*` command grouped by what it's for, or show
one command's full spec without leaving the terminal. Read-only, no library
required.
…

Under the hood

No script — Claude reads commands/help.md directly and, for a named command, the matching commands/<name>.md.

/ref:lint

phase 11+read-only

Read-only maintenance lint: list incomplete metadata/full-text state, repo integrity gaps, and stale checks with direct next-action commands.

/ref:lint [--stale-days <N>] [--json] [--snapshot]

Arguments

--stale-days <N>
Optional age threshold in days for stale checks. Default 180.
--json
Optional machine-readable report.
--snapshot
Optional. Also write the report to maintenance/<UTC-timestamp>.json in the library root.

What happens

  1. Scans every paper folder and buckets PMIDs by maintenance issue class.
  2. Flags metadata gaps (missing_title, missing_year, missing_journal, missing_doi), completeness gaps (metadata_only, abstract_only, oa_pending), and integrity gaps (missing_meta, missing_current, missing_claim_registry).
  3. Flags stale checks when checked_at is older than the threshold.
  4. Reports compact recommended follow-ups, e.g. /ref:index --rebuild, /ref:audit, /ref:fetch, /ref:extract.

Reads & writes

Reads paper records and index presence. Writes nothing unless --snapshot is passed, in which case it writes one timestamped JSON report under maintenance/.

Example

illustrative output

› /ref:lint --stale-days 180
papers_total: 124
issues_total: 39
catalog_present: true

issues:
- abstract_only: 18 [40665956, 40691132, ...]
- missing_claim_registry: 11 [40510001, 40510002, ...]

recommended next actions:
- run /ref:audit
- run /ref:fetch <pmid...> or /ref:add-fetch <pmid...>
- run /ref:extract <pmid...>

Under the hood

lint.py run --repo <library_root> [--stale-days N] [--json] [--snapshot].

/ref:repair-fulltext

phase 11+PubMed MCPUnpaywall

Batch-repair full-text gaps found by /ref:lint: work through metadata_only, abstract_only, and oa_pending PMIDs with the same per-PMID acquisition workflow as /ref:fetch, bounded by --limit and resume-safe across runs.

/ref:repair-fulltext [--limit <N>] [--stale-days <N>] [--retry-failed] [selector]

Arguments

--limit <N>
Optional. Max PMIDs attempted this run. Default 20.
--stale-days <N>
Optional. Passed to the underlying /ref:lint bucket selection. Default 180.
--retry-failed
Optional. Without it, PMIDs marked failed/abstract_only in the resume state within the last 24h are skipped.
selector
Optional. Restrict candidates to a /ref:search-style selector match before batching.

What happens

  1. Runs /ref:lint --json and unions the metadata_only, abstract_only, and oa_pending buckets into a candidate list.
  2. Loads per-PMID resume state from maintenance/repair-fulltext-state.json and skips recently-attempted candidates unless --retry-failed is set.
  3. Takes the first --limit remaining candidates and runs /ref:fetch's acquisition workflow on each, independently.
  4. Writes each attempted PMID's result and timestamp back to the resume state file.
  5. Prints a summary with counts and, when candidates remain, a suggested re-run.

Reads & writes

Reads lint output and paper records. Writes full-text/version data the same way /ref:fetch does, plus maintenance/repair-fulltext-state.json bookkeeping (never papers/<pmid>/ directly).

See also

/ref:lint · /ref:fetch · Maintenance tutorial

/ref:list

library viewerread-only

Filterable browse/report over the paper library: metadata, source coverage, lint issues, project/reading state, and a coverage matrix. Built on the same lib_inventory.rows() every other view uses. No filters lists every paper; a filter combination matching nothing prints an explicit message rather than nothing.

/ref:list [--source <badge,...>] [--has/--missing <key,...>] [--tier <t>] [--year <YYYY|YYYY..YYYY>] [--journal <substr>] [--retracted] [--stale-days <N>] [--issue <bucket>] [selector] [--sort <field>] [--columns <col,...>] [--format table|csv|json|pmids] [--matrix]

Arguments

--source <badge,...>
Subset of pdf-backed,full-text,oa-pending,abstract-only,metadata-only.
--has / --missing <key,...>
Presence filters (ANDed), subset of pdf,fulltext,claims,figures,notes.
--tier <abstract|full|unavailable>
meta.json.extraction_tier.
--year <YYYY|YYYY..YYYY>
Single year or inclusive range.
--journal <substring>
Case-insensitive.
--retracted
retraction_status is retracted or erratum.
--stale-days <N>
Only papers whose checked_at is older than N days.
--issue <lint-bucket>
One of the buckets /ref:lint reports.
selector
--project, --reading-status, --query, --from-file — the shared selector grammar; --reading-status requires --project.
--sort <year|added|title|checked|claims>
Sort order.
--columns <col,...>
Projection for table/csv/json; omit for the default column set.
--format <table|csv|json|pmids>
Default table. pmids prints a bare space-separated PMID list — pipe it straight into /ref:fetch / /ref:extract.
--matrix
Paper × {meta, abstract, fulltext, pdf, figures, claims, indexed, retraction} coverage grid instead of --columns.

Reads & writes

Reads paper records and index presence. Writes nothing.

Example

illustrative output

› /ref:list --issue abstract_only --format pmids
40665956 40691132 40701004
› /ref:list --source abstract-only,oa-pending --stale-days 180 --sort checked
pmid       title                                  year  source        checked
40665956   Sham tDCS and social cognition in...  2024  abstract-only  2026-02-11

Under the hood

list.py --repo <library_root> [flags above].

/ref:dashboard

library viewerread-only except notes

Dashboard over the paper library: health state, source coverage, pipeline funnel, papers-by-year, lint trend, a searchable/sortable paper table with the coverage matrix folded in as a per-row strip (click a column header to filter to papers missing it), per-project reading progress, an Insights tab of interactive evidence views (knowledge graph, gap grid, topic clusters, evidence maturity), maintenance sparklines, a paper panel, and a PDF viewer. Built on the same lib_inventory.rows()/detail() every other view uses.

/ref:dashboard [--port <n>] [--open] [--view '<query>'] /ref:dashboard --static [--open]

Arguments

--static
Build the static self-contained HTML dashboard instead of serving (also triggered by the literal word build).
--port <n>
Serve mode only. Fixed port instead of an OS-assigned one.
--open
Open the dashboard in the default browser once ready.
--view '<query>'
Serve mode only. Reopen a shared view: the query a Copy as command button produced, e.g. tab=insights&insight=graph&center=c:tdcs&hops=2. Accepted keys: tab, q, project, issue, source, sort, insight, center (p:<pmid> or c:<concept-id>), hops; anything else, such as a token, is refused.

What happens

Default (serve): a local HTTP server on 127.0.0.1 with a live API, an in-page pdf.js viewer (thumbnails, zoom, fit-width, page jump, find-in-PDF), and notes that save immediately through note.py append — the same file/format as /ref:note. Binds 127.0.0.1 only, with a random per-run token required on every request and checked against Host/Origin — not reachable from other machines or other browser tabs without the token in the URL. Blocks until interrupted (Ctrl-C).

--static: writes atomically to reports/dashboard/ (template + inline rows/lint JSON, one details/<pmid>.js per paper loaded on demand). No server; the PDF tab opens in a new browser tab instead of in-page. The notes composer only writes a browser-local draft with a "Copy /ref:note" button — committed notes still come from /ref:note.

Both modes: selecting rows in the Papers tab builds ready-to-copy /ref:fetch / /ref:extract commands for papers that still need them.

Insights tab (both modes): views computed in the browser from active claims, graph/concepts.jsonl, graph/relations.jsonl, MeSH terms and /ref:review batches, scoped to the Papers filters plus a year range.

  • Notable cards: best-connected paper, open conflicts, single-study findings, papers with no claims, growing and fading topics.
  • Evidence map: any two claim fields as a grid, coloured by direction, extraction tier or paper count.
  • Gaps: a population × outcome grid per intervention concept using the same rule as /ref:gaps, heuristic sparse pairs, single-study findings and unresolved conflicts.
  • Topic timeline.
  • Knowledge graph: Concepts, Papers & authors, Claim network, and a 1–2 hop Neighborhood around a paper or concept. Each relation type and review state has its own line and glyph (+ = » ? ✕, stale faded), and the relation detail panel lists supporting claims with differing comparability fields marked ≠ and a /ref:weave review command to copy. Nodes drag, the background pans, ⌘/Ctrl + scroll zooms, Shift + arrows move a node, and every mode has a Table view.
  • Clusters: cards with a papers-per-year sparkline and a growing / stable / fading label (last five years vs the five before), or a map of clusters sharing papers.
  • Maturity: per intervention concept, papers, outcome breadth, coverage, full-text share and open conflicts shown separately, with GRADE and risk-of-bias batches overlaid per batch.
  • Synthesis draft in Markdown.

Read-only; walkthrough in Evidence insights.

Reads & writes

Reads the same inventory/lint data as /ref:list and /ref:lint; the Insights tab also reads claim registries, graph/concepts.jsonl, graph/relations.jsonl, raw PubMed responses, and reviews/<batch>/ / projects/<slug>/reviews/<batch>/. Serve mode caches that payload and rebuilds it when those files change (the refresh button always rebuilds). Serve mode's notes composer is the only thing that writes to the library, via note.py append. Static mode writes only reports/dashboard/; a failed build never touches the previous snapshot.

Example

illustrative output

› /ref:dashboard --open
dashboard serving: http://127.0.0.1:53211/?token=9f2c...  (Ctrl-C to stop)
› /ref:dashboard --static --open
dashboard built: /Users/you/refs/reports/dashboard/index.html

Under the hood

dashboard.py serve --repo <library_root> [--port N] [--open], or dashboard.py build --repo <library_root> [--open] for --static.

/ref:audit

phase 11PubMed MCP

Re-check retraction and erratum status across the library, or record and show dated cited-by observations.

/ref:audit [selector] /ref:audit --citations [selector] /ref:audit show-citations [--stale-days N] [selector]

Arguments

[selector]
Optional selector (<pmid…>, --project, --study, --search, --from-file, …) to scope the sweep. Unlike other selector commands, no selector means the whole library, not an error: this is a maintenance sweep, not a saved set.
--citations
Record citation observations instead of retraction checks. Run the two modes separately.
show-citations
An action, not a flag. Print each PMID's latest real observation and whether it is stale, without checking anything new.
--stale-days N
For show-citations: age threshold in days (default 180).

What happens

Default mode (retraction status):

  1. For each resolved PMID, Claude calls get_article_metadata and checks article_types for a retraction, erratum or correction marker. This is the same check /ref:extract runs at ingestion.
  2. A successful check updates retraction_status in meta.json and reports whether it changed. A failed check leaves the prior status untouched and prints a diagnostic. It never guesses "none" or downgrades an earlier "retracted".
  3. If any status changed, propagate lists saved /ref:brief, /ref:compare and /ref:summarize artifacts that used those papers. They are not refreshed automatically; you run --refresh on them, and their earlier frozen versions are kept.

--citations mode: for each PMID, a paper with no PMCID gets a no_pmcid marker; otherwise Claude fetches NCBI's pubmed_pmc_refs ELink ("Cited in PMC") for that PMID directly over WebFetch, one PMID at a time. A failed/unparseable response gets a check_failed marker; a real count is stored with source pmc_elink, the exact query URL, a coverage note, and the retrieval date. Every call appends to citations.json; earlier entries are never overwritten, and a failure never becomes a zero.

Coverage is PMC-only. pmc_elink counts only citing articles that are themselves indexed in PMC — it undercounts total literature citations. No PubMed MCP tool provides a citation-graph count (related-article similarity is not citation), so this direct NCBI E-utilities call is the real source, not a fabricated one.

show-citations: skips check_failed and no_pmcid markers and shows the most recent real observation. A PMID with none shows null, which means "no observation available", not zero.

Reads & writes

Retraction mode updates papers/<pmid>/meta.json (retraction_status). --citations appends to papers/<pmid>/citations.json. propagate and show-citations only read: saved artifact manifests under tables/, summaries/, briefs/ (library-wide and per project), and citations.json.

Example

output from a scratch library (check results written by hand)

› /ref:audit
31452104: checked (none -> retracted) [CHANGED]
30679568: check_failed -- prior status retained (unknown); get_article_metadata timed out
# followed by the same results as JSON, ending in:
  "changed_pmids": [
    "31452104"
  ]
# propagate: which saved artifacts used the changed paper
{
  "changed_pmids": [
    "31452104"
  ],
  "potentially_stale_artifacts": []
}
› /ref:audit show-citations 31452104
[
  {
    "pmid": "31452104",
    "latest_observation": null,
    "stale": null
  }
]

Under the hood

audit.py retraction --repo <library_root> --results-file <json> [selector], then audit.py propagate --repo <library_root> --results-file <changed-pmids-json>; audit.py citations --repo … --results-file … [selector]; audit.py show-citations --repo … [--stale-days N] [selector]. The script never calls PubMed; Claude supplies the check results as JSON.

/ref:index

phase 0refresh: phase 8

Rebuild the SQLite search catalog from committed records and flag graph relations whose evidence has changed.

/ref:index --rebuild

Arguments

--rebuild
Required. It is currently the only supported mode.

What happens

  1. Deletes index/catalog.sqlite and recreates it from scratch. Files are the authority and the catalog is only a projection, so rebuilding beats migrating in place.
  2. Indexes one row per paper from meta.json (including retraction status), paragraphs of each paper's current source.md into passages_fts (headings become section labels), and every claim in claim_registry.json, whether active or superseded, into claims and claims_fts.
  3. Only what current.json points at is read; incomplete staging directories are ignored. Running it twice gives the same result.
  4. If graph/relations.jsonl exists, a relation refresh sets stale: true on any relation whose supporting claims are no longer active. A review decision is never cleared, only flagged for re-confirmation, and the stale relation IDs are reported.

Reads & writes

Reads papers/*/meta.json, current.json, versions/<v>/source.md, claim_registry.json. Writes index/catalog.sqlite and, when present, updates graph/relations.jsonl (stale, stale_reason).

Example

output from a scratch library

› /ref:index --rebuild
catalog rebuilt: 2 paper(s), 0 passage(s), 1 claim(s) indexed
# passages come only from source.md in the version current.json names;
# here /ref:extract committed last, and its version holds claims, not source.md
# with a graph present, the relation refresh then prints JSON of the form
# {"relations_checked": N, "went_stale": [relation IDs]}

Under the hood

catalog.py rebuild --repo <library_root>, then, if graph/relations.jsonl exists, relation.py refresh --repo <library_root>.

/ref:status

phase 0read-only

One-line health state, what needs attention, and what to run next — then catalog counts, extraction-tier breakdown, source completeness, project summaries, and a few recent papers. Read-only.

/ref:status

Arguments

None.

What happens

  1. Reads the config file. If none exists, it errors and points you at /ref:init; it never guesses a path.
  2. Prints the library root, and errors — naming the exact fix command — if that directory no longer exists.
  3. Leads with status: <state> — healthy, empty, not indexed, needs metadata, needs full text, or no active project — derived from the same counts printed below it, not a separate check.
  4. Prints a needs attention list and up to three suggested next actions (real commands, e.g. /ref:index --rebuild, /ref:fetch, /ref:project create <slug>) whenever the library isn't fully healthy.
  5. Prints papers-by-extraction-tier, source/completeness counts, per-project summaries, and a short list of recent papers.
  6. Each recent paper carries a concise source badge — full-text, pdf-backed, oa-pending, abstract-only, or metadata-only — so you can see acquisition state at a glance without opening records. Claude keeps this compact; the goal is quick orientation, not a substitute for full search.

Reads & writes

Reads ~/.config/ref-manager/config.json, index/catalog.sqlite, projects/, and papers' meta.json for source/completeness state. Writes nothing.

Example

output from a scratch library (paths shortened)

› /ref:status
status: not indexed
library: /private/tmp/…/scratch/lib
papers: 2 (0 indexed)  projects: 0

needs attention:
  - catalog not fully indexed (0/2 papers)
  - 1 paper(s) without full text (abstract-only or metadata-only)
  - no active project

suggested next actions:
  - /ref:index --rebuild
  - /ref:fetch to acquire full text for open-access papers
  - /ref:project create <slug> to start organizing papers

papers by extraction tier:
  full: 1
  abstract: 1
  unavailable: 0
papers by source/completeness:
  full_text: 1
  pdf_backed: 0
  oa_pending: 0
  abstract_only: 1
  metadata_only: 0
projects with questions: 0
recent papers: 2
  - 10000001: [full-text] … (rivera2019cortical, 2019) […]
  - 10000002: [abstract-only] … (chen2019editorial, 2019) […]

Under the hood

status.py (no arguments).

/ref:open

phase 3Papers.app

Open a paper's acquired PDF in Papers.app for reading and annotating.

/ref:open <pmid>

Arguments

<pmid>
Required. The paper must be in the library.

What happens

  1. Finds the paper's acquired PDF under raw/<sha256>/.
  2. If there is none, reports no_pdf_acquired and points at /ref:fetch or /ref:attach. This is not an error.
  3. Otherwise runs open -a Papers <pdf>, just like double-clicking the file in Finder, and reports opened with the path.

This is the only ref-manager command that touches Papers.app itself, and it never touches the Papers database. Highlights you make there come back with /ref:pull-annotations.

Reads & writes

Reads papers/<pmid>/meta.json and the acquired PDF. Writes nothing in the library; Papers.app receives the file.

Example

output from a scratch library

› /ref:open 31452104
{
  "pmid": "31452104",
  "status": "no_pdf_acquired",
  "message": "no acquired PDF for this paper yet — run /ref:fetch or /ref:attach first"
}

illustrative output

› /ref:open 31452104
{
  "pmid": "31452104",
  "status": "opened",
  "path": "<library_root>/papers/31452104/raw/<sha256>/source.pdf"
}

Under the hood

open_in_papers.py <pmid> --repo <library_root>; PDF lookup shared with export_papers.py.

/ref:pull-annotations

phase 4Papers.app

Copy your Papers.app highlights and margin notes for one paper into its record, one-way and without loss.

/ref:pull-annotations <pmid>

Arguments

<pmid>
Required. The paper must already exist (/ref:add first).

What happens

  1. Claude looks for ~/Library/Application Support/Papers/*.db and passes the first match. If there is none, the result is no_papers_db_configured, not a failure.
  2. The live database is copied with SQLite's backup API from a read-only connection, and all reads happen on that copy. If no consistent copy can be taken, the result is snapshot_unavailable.
  3. The Papers item is matched by PMID, falling back to DOI. No match gives no_matching_papers_item, meaning the paper isn't in your Papers library.
  4. Annotations are upserted by their own Papers id, into added, updated or unchanged. A repeat pull with no upstream changes reports everything unchanged and never duplicates.
  5. An annotation deleted in Papers since the last pull is tombstoned (deleted_upstream: true with a timestamp), not deleted locally, and listed under tombstoned. An accidental deletion or sync hiccup in Papers never silently erases evidence you already had.

Your free-text notes.md (from /ref:note) is never touched; annotations and notes are stored separately.

Reads & writes

Reads papers/<pmid>/meta.json and a snapshot of the Papers database. Writes papers/<pmid>/annotations.json (with papers_item_id and last_pulled_at). Never writes to Papers.

Example

output from a scratch library

› /ref:pull-annotations 31452104
# no Papers database on this machine
{
  "pmid": "31452104",
  "status": "no_papers_db_configured"
}

illustrative output

› /ref:pull-annotations 31452104
{
  "pmid": "31452104",
  "status": "ok",
  "added": ["<annotation id>"],
  "updated": [],
  "tombstoned": ["<annotation id>"],
  "unchanged": ["<annotation id>", "<annotation id>"]
}

Under the hood

pull_annotations.py --repo <library_root> --pmid <pmid> [--papers-db <path>]; snapshot access via papers_snapshot.py.
