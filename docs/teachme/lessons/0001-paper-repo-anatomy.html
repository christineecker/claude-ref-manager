Lesson 0001 · Maintaining the claude-ref-manager paper repo

Paper Repo Anatomy

What a library actually contains on disk, and who is allowed to write each file.

Primary source: docs/concepts.html, section “Library layout.” Everything below is taken from there — it in turn is derived from the actual scripts in skills/ref-manager/scripts/, not from PLAN.md, so where code and plan disagree, the doc (and this lesson) follow the code.

The one command that creates the skeleton

/ref:init <path> runs init_repo.py. That's it — it creates log.md and the top-level directories, then records the library root in ~/.config/ref-manager/config.json. Nothing below the top level exists yet; every other file is created lazily, on first write, by whichever command needs it.

Anatomy of one paper

Everything about a single PMID lives under papers/<pmid>/:

papers/<pmid>/
  meta.json          # bibliographic authority, citekey, extraction_tier   (add.py)
  authorship.json    # ordered author list, raw_order_preserved           (add.py)
  funding.json       # funding observations + state                      (add.py, fetch.py)
  raw/<sha256>/       # immutable, content-addressed
    response.json    # metadata envelope as resolved                     (add.py)
    source.jats | source.html | source.plain_text                        (fetch.py)
    source.pdf, attachment.json                                          (attach.py)
  current.json       # {"version": "v-..."} — atomic pointer
  versions/<v-id>/
    manifest.json    # source/converter/hash, or extractor/model/prompt versions
    source.md        # converted full text
    figures/
    figures.json     # figure assets, captions, cached vision entries
    claims.json      # claims emitted by this extraction run
    claim_registry.json  # cross-version claim history, supersession links
    notes.md         # /ref:note — never touched by extraction
    annotations.json # /ref:pull-annotations — upsert, tombstones on upstream delete
    corrections.json # /ref:verify review overlays
    citations.json   # append-only cited-by observations (D25)
    related.json      # /ref:related snowball candidates

Three things worth burning into memory, because they explain a lot of the rest of the codebase:

  1. raw/<sha256>/ is immutable and content-addressed. Re-fetching the same source never overwrites it — a new hash gets a new directory. This is how the repo avoids ever silently losing an earlier version of a source document.
  2. current.json is an atomic pointer, not the data itself. It just says which versions/<v-id>/ is "current." Extraction re-runs create a new version directory and flip the pointer — they don't mutate an old version in place.
  3. Ownership is per-file, not per-directory. notes.md is yours — extraction commands are documented to never touch it. claims.json is extraction's — you don't hand-edit it, you go through /ref:verify (which writes to corrections.json, an overlay, rather than editing claims directly).
Why an overlay instead of editing claims.json directly? It keeps every claim traceable to the extraction run that produced it, while still letting a human correct it. If corrections.json didn't exist, a manual fix would look indistinguishable from a model output — you'd lose the ability to ask "was this claim ever model-generated, or did a human always believe this?"

Everything above the papers/ level

Briefly, so you know where to look before diving into a specific tutorial later:

  • projects/<slug>/ — a project's scope, questions, paper membership, screening decisions, and every batch output (tables/, summaries/, briefs/, reviews/, checks/, prisma/) each in its own <batch>/ directory with a manifest.json.
  • people/<slug>.json — name variants and ORCID matches, split into confirmed/candidate/rejected.
  • labs/ and grant... directories exist in the skeleton but nothing writes to them yet as of this doc.
