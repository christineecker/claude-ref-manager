The Maintenance Loop

Which commands keep a library healthy, what each one actually touches, and how they chain together.

Primary source: commands/maintain.md, commands/lint.md, commands/status.md, commands/audit.md, commands/repair-fulltext.md. These are the actual shipped specs, not PLAN.md — where they diverge, this lesson follows the specs. Full detail table: Maintenance Command Cheat Sheet.

Two questions, two tools

Maintenance splits into glance and diagnose, and the repo gives you a separate command for each rather than one that tries to do both:

  • /ref:status — a one-line health state (healthy, needs full text, no active project, …), a short "needs attention" list, and up to three suggested next actions. Fast, meant for orienting at the start of a session.
  • /ref:lint — the real sweep. Read-only, but exhaustive: every PMID missing a title/year/journal/DOI, every paper stuck at metadata_only/ abstract_only/oa_pending, every stale retraction check, whether the catalog index is even present or has drifted from the files on disk (catalog_stale).

status is derived from the same counts lint would give you in full — it's a summary, not a separate check. Run status to decide whether it's worth running lint at all.

Once you know what's wrong, two more tools fix it

  • /ref:repair-fulltext takes lint's metadata_only/abstract_only/oa_pending buckets and works through them, one PMID at a time, using the same acquisition path /ref:fetch uses. It's bounded (--limit, default 20) and resume-safe: a state file (maintenance/repair-fulltext-state.json, owned exclusively by repair_state.py) tracks what was attempted and when, so re-running after an interruption makes forward progress instead of re-hammering the same failures.
  • /ref:audit re-checks retraction/errata status against PubMed. It's the one selector-taking command in the whole plugin where no selector means the whole library, not an error — because this is explicitly a maintenance sweep, not a scoped artifact. A second mode, --citations, records dated PMC "cited by" counts via a direct NCBI ELink call (there's no MCP tool that returns real citation counts — this was confirmed by checking, not assumed).
What "fix" doesn't mean: repair-fulltext never invents a success. A paper with no legitimate open-access full text just stays abstract_only across runs — that's the correct outcome, not a bug to chase. And when audit flips a paper's retraction status, it doesn't quietly patch every document that ever cited it: it names the potentially_stale_artifacts (a saved brief, comparison, summary) and leaves refreshing them to an explicit --refresh call. Nothing frozen gets silently overwritten.

The orchestrator

/ref:maintain runs status → lint --snapshot → index rebuild (catalog.py rebuild, plus relation.py refresh if a concept graph exists) → audit's retraction sweep, in that order, then prints a short next: list of concrete follow-up commands based on what it found. It is explicitly documented as not a replacement for any of the four commands it wraps — each stays useful on its own, and each stage is independent, so one stage failing doesn't block the later read-only ones.

The one thing maintain adds beyond "run four commands in sequence": every lint run it triggers is snapshotted to maintenance/, which is what makes /ref:lint --diff possible later — comparing today's gaps against last week's. 

/ref:maintain
  status.py                          -> health line
  lint.py --snapshot                 -> gap buckets, written to maintenance/
  catalog.py rebuild                 -> index refresh (skippable: --no-index)
  relation.py refresh                ->   (only if graph/relations.jsonl exists)
  audit retraction sweep + propagate -> status changes (skippable: --no-audit)
  next: -> concrete follow-up commands
