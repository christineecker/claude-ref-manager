Lesson 0003 · Maintaining the claude-ref-manager paper repo

The Acquire-to-Extract Pipeline

A PMID's full walk from bare number to structured claims: /ref:init → /ref:add → /ref:fetch → /ref:extract.

Primary source: commands/{init,add,fetch,extract}.md and agents/ref-extractor.md — the actual shipped specs. Quick-reference version: Pipeline Command Cheat Sheet. This lesson builds on Lesson 0001 (what gets written where) — if raw/<sha256>/, current.json, or versions/<v-id>/ aren't familiar yet, skim that first.

The shape of the pipeline

Four stages, each one command, each one only doing its own job:

/ref:init <path>      -> creates the library skeleton, once
/ref:add <pmid...>    -> resolves PMID -> metadata, creates papers/<pmid>/
/ref:fetch <pmid...>  -> acquires full text into a new versions/<v-id>/
/ref:extract <pmid...> -> reads full text (or abstract) -> claims.json

Every stage after init is independent and re-runnable. fetch augments a record that add already created; it never creates one from scratch. extract never blocks on missing full text — an abstract-only paper still extracts, just from less evidence. This is deliberate: you can stop after any stage and the paper is still usable, just at a lower evidence tier.

Stage 1 — /ref:init <path>

Run once per library. Creates log.md and the top-level directories at <path>, then records that path in ~/.config/ref-manager/config.json. Every other command reads the library location from that config file — you never pass --repo yourself again after this.

One library is "active" at a time. Re-running /ref:init against a different path without --force refuses to reconfigure — a safety rail against accidentally pointing every future command at the wrong library.

Stage 2 — /ref:add <pmid...>

PMID is the identity key for this whole system — nothing exists until it has resolved to one. add calls the PubMed metadata tool for every given PMID in a single batched call, then normalizes each result (title, abstract, authors in PubMed's original order, journal, year, DOI, PMCID, grants) and commits it.

This is what actually appears on disk after add:

papers/<pmid>/
  meta.json         # title, year, doi, pmcid, citekey, extraction_tier
  authorship.json   # ordered author list
  funding.json       # from any grants PubMed reported
  raw/<sha256>/response.json   # the metadata envelope exactly as resolved

Note what's not there yet: no versions/ directory, no current.json. A freshly-added paper is metadata-only. If PubMed returned no abstract, the paper is still added — flagged metadata-only, not treated as an error. Each PMID in a batch succeeds or fails independently; one bad ID never blocks the rest.

Stage 3 — /ref:fetch <pmid...>

fetch requires the paper to already exist (meta.json from add) — it augments, never creates. It tries sources in a strict priority order, stopping at the first that succeeds:

Fetch does not call add for you. Run /ref:fetch on a PMID that was never added and it fails loudly, per-PMID, with pmid <id> has no meta.json -- run /ref:add first (fetch.py's own check, before it tries any source). Other PMIDs in the same batch are unaffected — this is the same one-failure-never-blocks-the-rest independence every stage in this pipeline has, just triggered by a missing prerequisite instead of a bad source. The two stages stay deliberately separate rather than fetch silently adding what's missing: add is the identity-resolution step (PLAN.md's RESOLVE+DEDUP), and collapsing it into fetch would let a full-text acquisition quietly create a paper record with no explicit resolution step behind it.
  1. PMC JATS XML (if the paper has a PMCID) — the highest-fidelity path: section headings, tables, math, and figure locators all survive. It's also the only path that produces figures.json, so it's always tried first.
  2. PubMed's full-text tool as a fallback when JATS isn't available or doesn't parse — this returns pre-extracted plain text, not markup, so structure is lost but the words survive.
  3. Unpaywall (a single deterministic REST call, keyed on the paper's DOI) — if it finds an open-access PDF location, that's recorded as oa_location_found, not downloaded automatically. You'd follow up with /ref:fetch-pdf or /ref:attach.
  4. Publisher HTML, fetched and handed in by whoever is running the command.
  5. Nothing worked — the paper stays abstract_only. This is a legitimate, expected outcome, not a failure state.

A successful fetch writes a new version:

papers/<pmid>/
  raw/<new-sha256>/source.jats            # the raw source, content-addressed
  versions/<new-v-id>/
    manifest.json    # source: pmc_jats | publisher_html | plain_text
    source.md         # the converted full text
    figures.json       # only for the JATS path
  current.json        # pointer flipped to the new version

Re-running fetch on a paper whose source hasn't changed reports duplicate_noop and writes nothing new — it hashes the incoming source and compares against the current version's raw_hash first (you saw this content-addressing pattern already in Lesson 0001's PDF quiz). When a fetch does change the source, the old fetch-created version directory is pruned — but the raw bytes under raw/<sha256>/ are never deleted, so the evidence trail survives even after cleanup.

Stage 4 — /ref:extract <pmid...>

This is the one stage that isn't a deterministic script call. Classifying study type and normalizing a finding into PICO+ fields needs real reading judgment, so extract fans out one ref-extractor subagent per PMID, in parallel — every paper's extraction is independent, so one paper's malformed output or missing full text never blocks another's.

Each subagent gets exactly one paper's title, abstract, and full_text (or null if this paper never made it past Stage 2/3 — abstract-tier extraction still runs, per D4) and must return one JSON object: 

{
  "pmid": "...", "study_type": "rct|cohort|...|unknown",
  "study_type_confidence": "confident|uncertain",
  "claims": [
    {
      "locator": "...", "evidence_span": "<direct quote>", "evidence_tier": "abstract|full",
      "population": "...", "intervention": "...", "comparator": "...", "outcome": "...",
      "timepoint": "...", "direction": "...", "effect_value": "...", "effect_measure": "...",
      "uncertainty_interval": "...", "study_design": "...",
      "cohort_identity": "...", "adjustment_context": "..."
    }
  ]
}

Two rules worth internalizing, because they're what keep this trustworthy rather than just plausible:

  • Any field the subagent can't determine is the literal string "unknown" — never omitted, never guessed. A missing key would look like the extractor forgot to check; "unknown" makes the gap visible and machine-checkable.
  • Every claim carries an evidence_span — a direct quote, not a paraphrase — so a human reviewer can verify the normalization against the source text without re-reading the whole paper.

The calling command adds provenance the subagent has no access to (a source_hash of the text it was given, a fresh retraction_status check) before committing via extract.py, which writes claims.json and claim_registry.json into the current version directory. Re-extracting a paper whose new claim has the same locator as an old one but materially different content supersedes the old claim — a new claim_id is minted, the old one is kept with superseded_by set. Nothing is ever deleted; you saw this same immutable-history instinct in the raw/ directory back in Lesson 0001.

Watch it end to end

Every claim above is grounded in the command specs, but reading about it and watching it happen are different kinds of learning. Ask your agent to run these four commands in sequence against a real (or scratch) library and narrate what each one writes to disk as it goes — that turns this from something you've read into something you've seen.

A paper has no PMCID at all. You run /ref:fetch on it. What's the first thing it can still try?

Right — only the first path (JATS via PMC) needs a PMCID. Everything after it still runs in order.

Not quite — JATS is the only step that requires a PMCID. Without one, fetch just moves straight to PubMed's full-text tool, then Unpaywall (by DOI), then publisher HTML, before finally giving up.

You have a fresh PMID that's never been touched by this library. You run /ref:fetch <pmid> directly, skipping /ref:add. What happens?

Right — fetch augments an existing record, it never creates one. The two stages stay separate so identity resolution (add) is always an explicit step.

Not quite — fetch checks for meta.json first and fails that PMID loudly if it's missing, rather than creating or resolving identity itself. You still need /ref:add first.

A ref-extractor subagent can't determine a claim's timepoint from the text. What should it put in that field?

Right — every PICO+ field is required to be present, and "unknown" is the honest, explicit way to say "not determinable," never a guess and never a missing key.

Not quite — omitting the key or leaving it blank both hide the fact that the extractor genuinely couldn't tell. The contract requires the literal string "unknown" so the gap is visible and checkable.
