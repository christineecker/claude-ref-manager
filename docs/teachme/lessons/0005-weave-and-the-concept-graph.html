Lesson 0005 · Maintaining the claude-ref-manager paper repo

Weave and the Concept Graph

/ref:weave turns free-text claim fields into a graph of stable concepts and typed relations, then regenerates every derived view from that graph — the step PLAN.md calls WEAVE: “structured concepts/relations → generated OKF views.”

Primary source: commands/weave.md (the command spec) plus concept.py and docs/concepts.html for the MeSH-alias detail. This lesson assumes Lesson 0004 — weave consumes exactly the claim objects that lesson described.

Why no dedicated subagent

Concept mapping — deciding that a claim's free-text intervention/outcome is “the same thing” as an existing concept — needs judgment. PLAN.md only names two subagents, ref-extractor and ref-synthesizer, and neither fits this job. So /ref:weave does the mapping inline in the calling session, the same pattern /ref:check-citations already established for a different judgment task.

Two things live under one command name

PLAN.md's step 5 (WEAVE) bundles two halves that weave.md keeps as separate phases:

  1. Build/review the graph (steps 1–4, only when a selector is given): map claims to concepts, propose relation edges between claims that share a concept pair.
  2. Regenerate derived views (step 5, always run): rebuild the OKF bundle and the researcher/grant graph from whatever concepts/relations currently exist.

--regenerate-only (or omitting the selector entirely) skips straight to step 5 — useful after a /ref:verify correction or an /ref:extract rerun changes underlying data without adding new claims to weave.

Step 3–4: how a claim becomes a graph edge

For each active claim in the resolved papers:

  • Find before create. concept.py find is always called first. Only when no existing concept or alias matches does the command call concept.py create.
  • Near-matches become aliases, not new concepts. If a claim says “myocardial infarction” and a concept named “MI” already exists, the claim's wording is added via concept.py add-alias — one concept, two ways to spell it.
  • Edges only form between different papers. When two claims from different PMIDs map to the same subject/object concept pair, relation.py propose checks whether they report opposite directions (increase vs decrease) with matching comparator/effect_measure/timepoint/population. Only then does it return a proposal, and it is always potential_conflict — the deterministic check can't derive supports/ extends/replicates from PICO fields alone. A claim never gets compared against another claim from its own paper.
  • Judgment-based edges are explicit. When you (the agent) read two papers and judge that one genuinely extends or replicates another, that's relation.py create-manual --type supports|extends|replicates — a separate, stated-reasoning path, never something propose infers.
  • contradicts is never minted here. Promoting a potential_conflict edge to contradicts is always a separate /ref:weave review <relation-id> contradicts --rationale "..." action, and it's refused without a non-empty rationale.
concept.py never guesses a match. Its own docstring is explicit: matching is exact, case-insensitive, whitespace-normalized string comparison against a concept's name or its aliases list — nothing fuzzier. The judgment (is “MI” the same thing as “myocardial infarction”?) belongs to whichever agent calls find/create/ add-alias, not to the script.

What mesh terms are, here

MeSH (Medical Subject Headings) terms are PubMed's own controlled vocabulary, attached to a paper's metadata when it's fetched. They aren't a separate graph layer — docs/concepts.html states the mapping directly: “MeSH terms and other codes resolve to a concept's slug through its aliases.” A MeSH term is just one more string that can match (or be added as) an alias on a graph/concepts.jsonl row, exactly like a claim's free-text wording. There's no separate MeSH ingestion pipeline in this repo — the same find/create/ add-alias machinery from step 3 is what a MeSH code would go through if an agent chose to weave it in.

Step 5: two regeneration scripts, two purposes

Script Reads Writes
okf_emit.py graph/concepts.jsonl, graph/relations.jsonl, paper/people/grant records okf/ — a conformant OKF v0.2 bundle, readable by the okf plugin's search_concepts/ read_concept/get_neighbors MCP tools
graph_people.py committed authorship/funding data (phases 1–3) graph/people_relations.jsonl — researcher_authored_publication, publication_acknowledges_grant

graph/people_relations.jsonl is a deliberately separate file from graph/relations.jsonl (the scientific concept/claim graph from steps 1–4) — the two schemas were designed independently and merging them wasn't worth the risk. publication_supports_aim and researcher_lab_membership are schema-ready columns with nothing populating them yet: nothing in the plugin currently links a publication to a specific grant aim or lab-membership record, and the script says so plainly rather than fabricating a link.

Both scripts are pure regeneration: never hand-edit anything under okf/ or graph/people_relations.jsonl — edit the JSONL/JSON sources and re-run /ref:weave --regenerate-only.

The other two modes

/ref:weave review <relation-id> <type> --rationale "..." promotes or demotes a relation (e.g. potential_conflict → contradicts), and /ref:weave neighbors <concept-slug> answers “what supports/conflicts with/contradicts X” — the structural retrieval layer over the graph. Both skip steps 3–5 entirely and just print the matching relation.py subcommand's output verbatim.

Scope guardrail. Comparing every claim pair across a whole library is expensive and usually pointless. Weave-mode only compares claims already mapped to the same concept pair, and only within the papers the selector resolved to — never library-wide. A library-wide sweep is an explicit operation the calling agent batches by selector (e.g. one project at a time), never something this command does unprompted.
