Tutorial

Paper ingest: shortest paths

You have a research question, a stack of PDFs, or a Slack link someone sent you at 11pm — and none of them are in your library yet. This tutorial is the fast way in. For PICO intake, use /ref:pubmed-add-fetch: it searches, saves, adds, and fetches full text in one run, so you go from question to readable papers before your coffee gets cold. This tutorial stops once papers are in the library with text attached — for turning that text into structured, quote-backed claims, see the next tutorial.

Where papers actually live

All of this lands under the library root you picked when you ran /ref:init <path> — that path is saved once, in ~/.config/ref-manager/config.json, so no ingest command ever asks for it again. Every paper gets its own folder keyed by PMID, and that folder is the paper's entire life: metadata, raw bytes, converted text, notes, corrections. Nothing about a paper lives anywhere else.

~/Research/library/              # wherever you ran /ref:init — this is <LIBRARY> below
  papers/
    31452104/                    # one folder per PMID — the identity key, forever
    40665956/
    <pmid>/                      # every command in this tutorial writes inside here

See the data model for the full library layout and per-paper anatomy.

Every ingest command, one worked example

Each command below adds papers a different way. Outputs shown are the real examples from the command reference — nothing invented except placeholder PMIDs already marked as fixtures. Trees below are relative to <LIBRARY>/papers/<pmid>/ unless noted.

/ref:add <pmid…> — metadata only, no full text

The base case everything else builds on: resolve PMIDs through PubMed, write meta.json/authorship.json/funding.json. No fetch stage.

› /ref:add 31452104 30679568 99999999
# fixture PMIDs, not real papers
31452104: added (citekey=rivera2019cortical)
30679568: added (citekey=chen2019editorial) — no abstract available — metadata-only record, not fabricated
99999999: failed — no metadata returned for PMID 99999999
› /ref:add 31452104
31452104: already_present (citekey=rivera2019cortical)
One failed PMID never blocks the others. A re-add of an existing PMID is a no-op, reported as already_present.
papers/31452104/
  meta.json                   # bibliographic authority, citekey, extraction_tier
  authorship.json             # ordered author list
  funding.json                # funding observations, or state: "not_checked"
  raw/<sha256>/response.json  # immutable metadata envelope as resolved

Local files and URLs share one identify → add → attach/fetch shape

/ref:add-pdf <path…> [--force]

Already have the PDF on disk — a reviewer sent it, or you grabbed it before your VPN session died? This identifies it from its own bytes (DOI/PMID clues inside the file), runs /ref:add for the metadata, then attaches the PDF as that paper's full text.

› /ref:add-pdf ~/Downloads/luckhardt2025.pdf
~/Downloads/luckhardt2025.pdf: identified doi=10.1002/aur.70084 → pmid=40665956
40665956: added (citekey=luckhardt2025transcranial)
40665956: attached
papers/40665956/
  meta.json, authorship.json, funding.json    # from the add stage
  raw/<sha256>/source.pdf                     # your PDF bytes, untouched
  raw/<sha256>/attachment.json                # provenance of the attach
  versions/<v>/manifest.json                # + source.md when conversion succeeds
  current.json                                # atomic pointer → <v>

/ref:add-url <url…> [--no-fetch]

Paste a DOI link, a PubMed URL, or a journal page. This identifies the PMID from the URL, adds the metadata, then walks the same fetch ladder as /ref:fetch (PMC JATS → open-access PDF → abstract-only) to pull full text.

› /ref:add-url https://doi.org/10.1002/aur.70084
identify:
https://doi.org/10.1002/aur.70084: doi -> 40665956

add:
40665956: added (citekey=luckhardt2025transcranial)

fetch:
40665956: acquired (source=pmc_jats, figures=3, images=3/3)
papers/40665956/
  meta.json, authorship.json, funding.json    # from the add stage
  raw/<sha256>/source.jats                    # immutable, whichever source won the ladder
  versions/<v>/source.md, figures.json, manifest.json   # converted text + figure locators
  current.json                                # atomic pointer → <v>

/ref:add-fetch <pmid…> — add + fetch, orchestration only

Already have PMIDs (from a search, a colleague, a reference list) and just want full text? This is /ref:add then /ref:fetch chained — no new logic of its own, so it writes exactly the files each of those would write on its own.

› /ref:add-fetch 40665956 99999999
add:
40665956: added (citekey=luckhardt2025transcranial)
99999999: failed — no metadata returned for PMID 99999999

fetch:
40665956: acquired (source=pmc_jats, figures=3, images=3/3)
A PMID that failed to add is skipped at the fetch stage instead of producing a second, predictable failure.

/ref:import <item…> [--no-fetch] — mixed batches

Inherited a supervisor's Zotero export, a folder of PDFs, and three DOIs typed into a Slack thread? Dump it all in. One resolver (lib_intake.py classify) sorts every input into pmid, doi, url, pdf, bib_entry, csl_entry, or unknown — including expanding a folder of PDFs or parsing a .bib/.csl.json file into one entry per record.

› /ref:import 40665956 https://doi.org/10.1002/aur.70084 ~/Downloads/luckhardt2025.pdf
classify:
40665956: pmid -> already imported as 40665956
https://doi.org/10.1002/aur.70084: doi -> already imported as 40665956
~/Downloads/luckhardt2025.pdf: pdf(doi=10.1002/aur.70084) -> 40665956

add:
40665956: already_present (citekey=luckhardt2025transcranial)

fetch:
40665956: duplicate_noop
papers/40665956/   # unchanged by this run — already written by an earlier add-pdf/add-url
  meta.json, authorship.json, funding.json
  raw/<sha256>/source.pdf, attachment.json
  versions/<v>/source.md, manifest.json
  current.json
All three inputs here resolve to the same PMID — duplicate_in_batch is reported when that happens within one call, already_imported when it already matches a library paper. Neither is an error.

/ref:update-queries <slug> — rerun a saved search unchanged

For a running literature search you revisit weekly. This re-runs the exact query frozen in queries/<slug>.yaml and diffs the new hit list against the last saved run — it does not touch papers/ at all, only reports what changed.

› /ref:update-queries asd-cortex
{
  "run": {
    "run_id": "run-47456189b1d6",
    "query": "(\"Autism Spectrum Disorder\"[MeSH]) AND cortical thickness[tiab]",
    "source": "pubmed",
    "retrieved_at": "2026-09-15T10:14:34.789920+00:00",
    "pmids": ["31000001", "31000002", "39999992"]
  },
  "added": ["39999992"],
  "removed": ["39999991"]
}
queries/asd-cortex.yaml   # saved query expression + immutable runs[] history, appended to on rerun
The stored query expression is reused exactly — this is not a new search, just the same one run again. Pair with /ref:add-fetch on the added PMIDs to pull in full text.

No starting PMID? Two more routes

The decision map above assumes you already have a PMID, PICO question, URL, PDF, or mixed batch. Two other cases feed candidates in rather than an ID you already hold.

Snowball from a paper you already have

/ref:related <pmid> [--direction backward|forward|both] — backward reads the reference list out of already-committed full text (no network call); forward asks PubMed's find_related_articles for similar papers. Either direction only surfaces candidates in papers/<pmid>/related.json; nothing is added automatically.

illustrative output

› /ref:related 31000001 --direction forward
{ "count": 1, "rows": [
    { "candidate": "31000002", "resolved": true, "direction": "forward",
      "method": "find_related_articles:pubmed_pubmed", "already_in_library": false } ] }
› /ref:add-fetch 31000002
papers/31000001/
  related.json   # candidates only — nothing added to the library yet
pubmed_pubmed is similarity, not "cited by." There is no true citation-graph link type in the live MCP tool — record the exact link_type, don't call it a citation.

A researcher's back-catalog

Stalking a PI's publication history for a lit review? Confirm identity first, then let /ref:discover build the author query. Name similarity alone never creates a confirmed link — no accidental namesake papers sneaking into your bibliography.

illustrative output

› /ref:person create moreau-c --name "Moreau, Claire" --orcid 0000-0002-1825-0097
› /ref:discover --person moreau-c
{ "candidate_publications": [{ "pmid": "31000003", "title": "..." }] }
› /ref:person confirm-publication moreau-c --pmid 31000003 --author-index 2
› /ref:add-fetch 31000003
people/moreau-c.json   # name variants, ORCID, confirmed/candidate/rejected publication matches
Confirming identity still doesn't create a paper record — that's /ref:add (or /ref:add-fetch). A rejected candidate via /ref:person reject-publication is never re-suggested.

Minimal recipes

Copy, paste, adjust the slug. Done.

› /ref:pubmed-add-fetch "children autism tDCS sham social cognition" --slug asd-tdcs --create --limit 20
› /ref:update-queries asd-tdcs
› /ref:add-fetch 40665956 40691132
› /ref:import 40665956 https://doi.org/10.1002/aur.70084 ~/Downloads/papers/
