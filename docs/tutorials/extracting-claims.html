Tutorial

Extracting claims

You've got papers with full text or at least an abstract (see Adding papers). Now turn each one into structured, quote-backed findings with /ref:extract — what a claim actually is, what PICO means here, how claims survive a rerun, and how to correct one without ever editing extracted data in place.

What "extracting claims" means

/ref:extract doesn't summarize a paper — it pulls out every reported finding as its own structured record. A single paper with three reported results produces three separate claim objects. Extraction needs reading judgment, so Claude starts one ref-extractor subagent per PMID, all running in parallel; each reads the paper's committed full text if there is one, or its abstract otherwise. extract.py then validates whatever the subagent proposes, fills defaults, assigns IDs, and commits.

PICO, and the fields around it

PICO is the standard way clinical/scientific literature frames a finding: Population, Intervention, Comparator, Outcome — who was studied, what was done to them, what it was compared against, and what was measured. A claim needs more than that to be checkable, so ref-extractor reports twelve normalized fields per claim, all required (the literal string "unknown" counts as present — nothing is guessed to fill a gap):

PICO population · intervention · comparator · outcome Who, what was done, versus what, what was measured — the four fields the acronym names. When & how much timepoint · direction · effect_value · effect_measure · uncertainty_interval When the outcome was assessed, which way it moved, and the reported size, unit, and interval — each "unknown" if the text doesn't state it. Design context study_design · cohort_identity · adjustment_context This claim's own design (which can differ from the paper's overall study_type), which cohort it draws on, and what covariates it was adjusted for.

Full field-by-field reference: Concepts · the claim contract.

Run it

If no PMID is given, Claude runs the shared recent/unresolved picker instead of asking you to recall PMIDs from memory. Otherwise, pass one or more PMIDs — each just needs a meta.json already on record (see /ref:add).

output from a scratch library · claims written by hand in the subagent's output shape

› /ref:extract 99000001 99000002
  # spawns 2 ref-extractor subagents in parallel, then:
99000001: extracted (study_type=imaging, claims=1)
99000002: extracted (study_type=cohort, claims=1)
  • The tier only goes up. 99000001 had full text, so its extraction_tier becomes "full". A later rerun with thinner text never downgrades it. 99000002, abstract-only, stays "abstract".
  • Retraction status gets re-checked with get_article_metadata on every extraction. A failed or ambiguous check is saved as "unknown", never as "none" — silence is never read as "not retracted."
  • Reads meta.json and the current source.md or abstract. Writes versions/<v>/claims.json + manifest.json, updates current.json and claim_registry.json, and updates meta.json's extraction_tier / retraction_status / checked_at. Full reference: /ref:extract.

A claim, in full

Every claim carries three groups of fields, not one flat bag: the twelve PICO+ fields above (what was found), provenance fields (where it came from), and identity/lifecycle fields (how it's tracked over time). This is one committed claim for 99000001 — the same finding Get started retrieves later with /ref:ask:

output from a scratch library · versions/<v>/claims.json

{
  "claim_id": "c-d85223adbc65",
  "pmid": "99000001",
  "version_id": "v-<hash>",

  "population": "autistic adults",
  "intervention": "autism diagnosis",
  "comparator": "non-autistic controls",
  "outcome": "cortical thickness",
  "timepoint": "unknown",
  "direction": "increase",
  "effect_value": "0.41",
  "effect_measure": "Cohen's d",
  "uncertainty_interval": "95% CI 0.15-0.67",
  "study_design": "cross-sectional",
  "cohort_identity": "unknown",
  "adjustment_context": "unknown",

  "locator": "Results",
  "evidence_span": "Autistic adults showed increased cortical thickness in frontal regions (Cohen's d = 0.41, 95% CI 0.15-0.67).",
  "evidence_tier": "full",
  "study_type": "imaging",
  "source_hash": "<sha256>",

  "content_hash": "<sha256 of the 12 normalized fields + study_type>",
  "status": "active",
  "excluded_from_synthesis": false,
  "supersedes": null,
  "superseded_by": null
}
  • evidence_span is a direct quote, never a paraphrase — you can always trace a claim back to the exact sentence it came from.
  • study_type is the paper's overall design; this claim's own study_design can be more specific (a paper can be mixed overall while one claim inside it is a clean RCT sub-study).
  • status and excluded_from_synthesis are independent axes. A claim can be active and excluded (a human rejected it, nothing has superseded it yet), or superseded and never excluded (a routine rerun replaced it, no human judgment involved). Retrieval filters on both.

Claim IDs stay stable across reruns

claim_registry.json keeps every claim ever committed for a paper — nothing is ever deleted. Re-run /ref:extract on a paper, and for each incoming claim, extract.py compares it against whatever was active at that same locator before the run:

  1. Same content_hash: the claim keeps its existing claim_id. Nothing changed, so nothing new is minted.
  2. Hash differs, exactly one prior unconsumed claim at that locator: a genuine revision. The new claim gets a fresh ID and supersedes the old one; the old claim flips to status: "superseded" with superseded_by set — kept, not deleted.
  3. Hash differs, zero or several prior claims at that locator: ambiguous, so no supersession is asserted — the new claim just gets a fresh ID.

illustrative output · re-extracting after the source paper issued a correction

› /ref:extract 99000001
99000001: extracted (study_type=imaging, claims=1)
# at locator "Results", effect_value changed 0.41 -> 0.52 vs. the prior single active claim there:
# old claim -> status: superseded, superseded_by: <new claim_id>, still in claim_registry.json
# new claim -> fresh claim_id, supersedes: <old claim_id>
This is the same immutable-history instinct as raw/<sha256>/ for downloaded sources — nothing about a claim's history is overwritten, only superseded and kept.

Maintaining claims: corrections, not edits

Extracted data is never edited in place. A human review decision — accept, edit, or reject a specific claim — is recorded as a separate overlay with /ref:verify claim. Retrieval and synthesis read the claim plus its correction overlay together; the underlying claims.json stays exactly as extraction wrote it.

/ref:verify claim <pmid> <claim_id> accept|edit|reject [--replacement <json-file>] [--rationale "…"] [--reviewer "…"] /ref:verify show <pmid>

illustrative output

› /ref:verify claim 99000002 c-2b31957bd938 reject --rationale "Effect reported for adolescents, not adults"
{
  "correction_id": "cor-…",
  "target_type": "claim",
  "target_id": "c-2b31957bd938",
  "decision": "reject",
  "original_value": { "population": "…", "intervention": "…", "comparator": "…", "outcome": "…" },
  "replacement_value": null,
  "rationale": "Effect reported for adolescents, not adults",
  "reviewer": "user",
  "timestamp": "…",
  "status": "active"
}
  • reject flips excluded_from_synthesis to true on the claim in the registry. It does not touch status — "rejected" isn't a status value; status only ever tracks active/superseded, a supersession event, not a human judgment.
  • edit takes --replacement <json-file>, a corrected version of the claim's fields, recorded as an overlay rather than mutating claims.json.
  • Corrections carry over automatically when a rerun's evidence is unchanged. If re-extraction materially changes the evidence at that locator, the correction flips to pending_review instead of silently reapplying or silently dropping — /ref:verify show <pmid> revalidates and prints exactly that state.

Full command reference: /ref:verify.

Minimal recipes

› /ref:extract 40665956 40691132
› /ref:extract # no PMIDs -> picker over recent/unresolved papers
› /ref:verify claim <pmid> <claim_id> reject --rationale "…"
› /ref:verify show <pmid> # revalidate + print corrections, including any now pending_review
