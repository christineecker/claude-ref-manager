Maintenance loop

Minimal text. Weekly loop: status, lint, index, audit, repair — inspect state with /ref:list and /ref:dashboard.

Where maintenance state lives

Every stage below reads or writes something under your library root (the path from /ref:init, resolved via ~/.config/ref-manager/config.json). None of it lives outside the library, and maintenance/ is the one folder that exists purely for this loop — nothing else reads it.

<LIBRARY>/
  papers/<pmid>/
    meta.json                          # /ref:audit updates retraction_status here
    citations.json                     # /ref:audit --citations appends dated observations
  index/
    catalog.sqlite                     # /ref:index --rebuild; /ref:status and /ref:list read it
  maintenance/
    <UTC-timestamp>.json               # /ref:lint --snapshot — one file per snapshot, never overwritten
    repair-fulltext-state.json         # /ref:repair-fulltext resume bookkeeping

Loop

What /ref:lint flags

Read-only unless you pass --snapshot. Three bucket groups, each with its own routing suggestion baked into the report — you don't have to memorize which repair command fixes which bucket.

Inspecting state: /ref:list and /ref:dashboard

Read-only, run anytime — not part of the repair loop itself, but how you find what to feed into it.

ToolUse
/ref:list --issue <bucket> --format pmidsturn a lint bucket into a PMID list, piped straight into /ref:fetch//ref:extract.
/ref:list --source abstract-only,oa-pending --stale-days 180filter the same buckets by source state, tier, year, journal, or project without touching lint output.
/ref:list --matrixpaper x {meta, abstract, fulltext, pdf, figures, claims, indexed, retraction} coverage grid.
/ref:dashboardlocal server (default) — Papers/Coverage/Projects/Maintenance tabs, per-paper panel with PDF viewer and notes, live off lib_inventory/lint so it reflects what /ref:status and /ref:lint would report right now.
/ref:dashboard --staticwrites a static reports/dashboard/ snapshot to share or open from file:// — no server, no live notes.

Suggested cadence

One profile per row; run heavier stages less often than lighter ones.

ProfileRunWhy not more often
ad hoc/ref:list · /ref:dashboardread-only, no cadence — open the dashboard while triaging, or run /ref:list --issue … right after a /ref:maintain pass.
weekly/ref:maintain --stale-days 180status + lint + index rebuild + retraction audit — all read-only or idempotent, cheap to repeat.
monthly/ref:repair-fulltext --limit 20 (repeat until remaining: 0)each call does real network fetches; --limit and its resume state exist so a month-old backlog does not turn into one giant run.
quarterly/ref:audit --citationscitation counts move slowly; each call is a per-PMID WebFetch to NCBI, so scope it to a selector for a large library rather than the whole thing every quarter.

All three compose: a weekly /ref:maintain run's next: section names the PMIDs the monthly/quarterly passes should target.
